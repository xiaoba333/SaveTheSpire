# 《Save The Spire》玩家 / 敌人实体接口规范

> 项目：类杀戮尖塔 · 2D 回合制卡牌战斗游戏
> 模块：实体层（战斗单位）
> 包路径：`com.roguelike.dungeon.game`
> Java 版本：21（Maven `release=21`）
> 状态：接口规范（编码前先行对齐）

---

## 一、设计目标与原则

实体（玩家 / 敌人）是战斗系统的核心战斗单位。为避免把「血量、护甲、能量」这些属性
硬编码在每个实体里，本项目把每个属性能力抽象成**独立接口**，实体按需「拼装」实现。

带来的好处：

1. **低耦合** —— 卡牌、AI、状态效果只面向接口编程，不依赖具体实体类。
2. **可拓展** —— 新增「拥有护甲的新怪物」等无需改动核心逻辑。
3. **行为内聚** —— 扣血、叠甲、耗能这些规则各自收敛在一个接口里，便于维护与测试。
4. **团队并行** —— 5 人分工时，写卡牌的人只需要知道 `IArmor` / `IHealth` 接口即可。

---

## 二、接口总览

本项目抽象出三个「属性能力」接口：

| 接口 | 中文 | 职责 | 谁实现 |
|------|------|------|--------|
| `IHealth` | 血量 | 生命值增减、死亡判定 | 玩家、敌人 |
| `IArmor`  | 护甲 | 叠甲、吸收伤害、清空 | 玩家、敌人 |
| `IEnergy` | 能量 | 每回合能量、消耗校验、回合刷新 | **仅玩家** |

### 实现对照表

| 实体 | IHealth | IArmor | IEnergy |
|------|:-------:|:------:|:-------:|
| 玩家 `Player` | ✅ | ✅ | ✅ |
| 敌人 `Enemy`  | ✅ | ✅ | ❌ |

> **说明**：能量是玩家「出牌」专属资源；敌人由 AI 每回合自动行动，不消耗能量，
> 因此敌人不实现 `IEnergy`。若后续出现「会用能量的特殊怪物」，让它实现 `IEnergy`
> 即可，核心逻辑零改动。

## 三、接口详细规范

> 统一约定：所有属性均使用 `int`（与现有 `Combat` 代码保持一致）；
> 所有「增减」方法对非法入参（如 `amount <= 0`）**静默忽略**，不抛异常、不产生副作用。

### 3.1 IHealth —— 血量接口

生命值管理，是战斗胜负判定的唯一依据。**玩家与敌人都实现。**

```java
public interface IHealth {

    /** 当前血量。范围 [0, maxHealth]。 */
    int getHealth();

    /** 最大血量（血量上限，受 Buff 等影响可变动）。 */
    int getMaxHealth();

    /** 直接设置血量，内部自动夹在 [0, maxHealth] 区间。 */
    void setHealth(int health);

    /** 恢复 amount 点血量，不超过 maxHealth；amount <= 0 时忽略。 */
    void heal(int amount);

    /**
     * 扣除 damage 点血量（纯扣血，不含护甲结算）。
     * @return 实际扣除的血量（0 <= 返回值 <= damage）
     */
    int takeDamage(int damage);

    /** 是否死亡，即当前血量 <= 0。 */
    boolean isDead();
}
```

**边界约定：**

- 血量永远在 `[0, maxHealth]`，任何操作不得越界。
- `takeDamage` 负责扣血并夹到 0，返回「实际扣掉的量」供日志/事件使用。
- 死亡判定只认 `getHealth() <= 0`，不要用额外布尔字段记录（避免状态不一致）。

---

### 3.2 IArmor —— 护甲接口

护甲是「先于血量」结算的临时防护层，回合开始时清空（对标杀戮尖塔护盾机制）。
**玩家与敌人都实现。**

```java
public interface IArmor {

    /** 当前护甲值，范围 [0, +∞)。 */
    int getArmor();

    /** 叠甲：增加 amount 点护甲；amount <= 0 时忽略。 */
    void addArmor(int amount);

    /**
     * 护甲优先吸收伤害。
     * 护甲同步减少被吸收的部分，返回未被吸收的剩余伤害。
     * @return 剩余伤害（>= 0），需要继续由血量结算
     */
    int absorb(int damage);

    /** 清空护甲为 0（每回合开始时调用）。 */
    void clearArmor();
}
```

**边界约定：**

- 护甲非负，`addArmor` 不能导致护甲变成负数。
- `absorb(damage)` 内部逻辑等价于：
  `absorbed = min(armor, damage); armor -= absorbed; return damage - absorbed;`
- 护甲本身**不参与**死亡判定，只影响「最终扣多少血」。

---

### 3.3 IEnergy —— 能量接口（仅玩家实现）

能量是玩家每回合出牌消耗的资源，回合开始刷新到满值。**敌人不实现。**

```java
public interface IEnergy {

    /** 当前剩余能量，范围 [0, maxEnergy]。 */
    int getEnergy();

    /** 每回合能量上限。 */
    int getMaxEnergy();

    /** 直接设置能量，内部夹在 [0, maxEnergy] 区间。 */
    void setEnergy(int energy);

    /** 增加 amount 点能量，不超过 maxEnergy；amount <= 0 时忽略。 */
    void addEnergy(int amount);

    /**
     * 尝试消耗 cost 点能量。
     * @return true 表示消耗成功；false 表示能量不足（不扣任何能量）
     */
    boolean consume(int cost);

    /** 是否足以支付 cost 点能量（只判断、不扣除）。 */
    boolean canAfford(int cost);

    /** 刷新能量到满值（每回合开始时调用）。 */
    void refresh();
}
```

**边界约定：**

- `consume` 是「原子」操作：要么扣满 cost 并返回 true，要么完全不动返回 false。
  禁止出现「扣了一半发现不够」的情况。
- `cost <= 0` 视为合法（直接返回 true），方便卡牌基类统一调用。
- 出牌前必须先 `canAfford` 校验，**禁止超费出牌**（对应需求「卡牌消耗能量校验」）。

## 四、实体类设计

### 4.1 Player —— 玩家实体

实现三个接口：血量 + 护甲 + 能量。

```java
public class Player implements IHealth, IArmor, IEnergy {

    private int maxHealth;
    private int health;
    private int armor;
    private int maxEnergy;
    private int energy;

    public Player(int maxHealth, int maxEnergy) { ... }

    // 实现 IHealth / IArmor / IEnergy 全部方法 ...

    /**
     * 统一受击入口：护甲先吸收，剩余伤害由血量承担。
     * @return 实际扣除的血量
     */
    public int receiveDamage(int damage) {
        int remaining = absorb(damage);   // 护甲吸收
        return takeDamage(remaining);     // 血量承担剩余
    }
}
```

### 4.2 Enemy —— 敌人实体

实现两个接口：血量 + 护甲（无能量）。

```java
public class Enemy implements IHealth, IArmor {

    private int maxHealth;
    private int health;
    private int armor;

    public Enemy(int maxHealth) { ... }

    // 实现 IHealth / IArmor 全部方法 ...

    /** 与 Player 相同的受击逻辑。 */
    public int receiveDamage(int damage) {
        int remaining = absorb(damage);
        return takeDamage(remaining);
    }
}
```

> 说明：玩家与敌人在「血量 + 护甲 + 受击结算」上行为一致，后续可抽取公共基类
> `AbstractUnit` 复用 `receiveDamage` 逻辑，避免重复代码。规范阶段先约定好接口即可。

## 五、接口协作与伤害结算规则

跨接口的关键流程，统一按以下顺序（**全项目必须遵守的核心规则**）：

### 5.1 伤害结算（护甲 → 血量）

```
受到 damage 点伤害
   ↓
护甲吸收：remaining = armor.absorb(damage)
   ↓
血量结算：actualHpLoss = health.takeDamage(remaining)
   ↓
若 health.isDead() → 触发死亡事件 / 胜负判定
```

等价公式：`实际扣血 = max(0, damage - 护甲)`，护甲同步扣 `min(damage, 护甲)`。

### 5.2 出牌流程（仅玩家，能量 → 效果）

```
玩家选牌
   ↓
energy.canAfford(cost) ？ —— 否 → 提示「能量不足」，不打出
   ↓ 是
energy.consume(cost)（原子扣费）
   ↓
执行卡牌效果（攻击 → 敌人.receiveDamage / 防御 → 玩家.addArmor / 技能 → 挂状态）
```

### 5.3 回合刷新

```
玩家回合开始：
   energy.refresh()          // 能量回满（仅玩家）
   armor.clearArmor()        // 清空上回合残留护甲
   抽牌 ...

敌人回合：
   armor.clearArmor()        // 清空敌人残留护甲
   AI 决定行动（攻击 / 叠甲 / 挂状态），不消耗能量
```

## 六、边界与容错（对应需求「稳定性」）

| 场景 | 约定 |
|------|------|
| 能量不足出牌 | `canAfford` 拦截，`consume` 原子失败，UI 提示 |
| 牌堆为空 | 弃牌堆洗回抽牌堆（现有 `Combat.drawToHandSize` 已处理） |
| 单位已死亡 | 死亡单位不再响应任何伤害/增益；胜负判定只触发一次 |
| 扣血/叠甲为 0 或负数 | 各接口方法静默忽略 |
| 血量/能量越界 | 一律夹在 `[0, max]` 区间 |
| 护甲结算溢出 | 护甲非负，`absorb` 返回值非负 |

## 七、命名与代码规范约定

1. 接口命名：`I` 前缀 + 能力名（`IHealth` / `IArmor` / `IEnergy`）。
2. 方法命名：getter 用 `getXxx()`；变更动作用动词（`heal` / `takeDamage` / `addArmor` /
   `absorb` / `consume` / `refresh`）。
3. 字段命名：小驼峰（`maxHealth` / `health` / `armor` / `energy`）。
4. 注释：每个类、每个方法写中文 Javadoc（与现有 `Card.java`、`Combat.java` 风格一致）。
5. 属性类型统一 `int`，不引入包装类型，避免空指针。
6. 敌人**没有** `energy` 相关字段与方法，代码中不要出现 `enemy.getEnergy()` 之类调用。
