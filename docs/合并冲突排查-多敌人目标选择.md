## 二、排查方法（全程只读，不碰工作区与 refs）

因为改动还没提交，常规 `git merge` 无法直接模拟。这里用了三步：

1. **临时索引造树**——用 `GIT_INDEX_FILE` 指向 `target/_probe_index`，把工作区（含未跟踪文件、`.gitignore` 生效）读成 tree。
2. **游离 commit**——`git commit-tree <tree> -p 5e700ca` 造一个提交对象。**不写任何 ref**，纯游离对象。
3. **真实合并模拟**——`git merge-tree --write-tree --messages <ours> 76be79d`，直接给出冲突文件名。
4. **物化验证**——把合并出的 tree 展开到 `target/_merge_check/`，套用手工解法后 `javac` 编译。

这样得到的冲突结论和真实 `git merge` 一致，且对仓库零副作用。

## 六、语义风险（不报冲突，但必须处理）

### P1：`MonsterEncounterAi` 没有实现 `onHpDepleted`

上游把「变形」提升成了 `MonsterAi` 的一等契约，而我们新增的编队 AI 直接继承了默认实现
（恒返回 `false`）。后果是：

- 任何**走编队路径**、且带 `nextFormId` 的怪，血量归零后会直接死亡，不变形。
- 目前 `GameController` 的 BOSS 仍走单怪 `boss(...)`，所以**眼下不会触发**；
  但我们公开了 `MonsterCatalog.randomEncounter(EncounterCategory.BOSS, seed)` 与
  `encounter(String)`，一旦有 Boss/多形态遭遇注册进编队池，就会踩到。

**建议**：在 `MonsterEncounterAi` 里实现 `onHpDepleted`，对名册中血量归零且有 `nextFormId`
的怪就地换形态（复用已有的 `Context.transform` → `BattleState.replaceMonster` 保槽位），
并像 `ScriptedMonsterAi` 那样按怪实例维护一份蜕变层数，避免换形态时丢层。

### P2：Boss 变形会顺带切换到「名册模式」

上游 `ScriptedMonsterAi.onHpDepleted` 结尾调用 `state.bindLivingMonster(monster)`，
而我们把该方法改成了 `bindMonsters(List.of(monster))` —— 也就是变形后 Boss 会进入名册模式。

单只怪的名册与木桩语义等价（`isEncounterCleared()` ≡ `getMonsterHp() <= 0`，目标恒为 0 号），
本次物化验证已确认编译与冒烟通过；但这是一条**新出现的耦合**，建议在 Boss 蛋链上单独补一条
「打碎蛋 → 变形 → 四层蜕变 → 打0*9 变 9 段各 4 点」的回归用例。

### 途中踩到的两个坑

1. **`git merge-file` 不能直接用**：工作区文件是 CRLF、git blob 是 LF，
   行尾符不一致会让它把整个文件判成全冲突。可靠做法是用 `git merge-tree`
   出的合并树（ort 策略，行尾无关），或统一行尾后再三方合并。
2. **暂存区会骗人**：`MM` 状态说明索引里是旧基线内容。基线一前进，
   索引内容就变成「反向修改上游文件」。对齐基线后必须 `git reset` 一次。

## 十二、新发现的风险：单测 `RelicIntegrationTest` 偶发失败

执行过程中观察到一次全量单测失败：

```
--- FAIL: battleEndRelicShouldHealPlayerAfterVictory()
expected: <VICTORY> but was: <DEFEAT>
  at RelicIntegrationTest.java:132
```

排查结论（4 次全量里出现 1 次；单独跑该测试类 **12/12 全过**）：

- **根因不在本次改动**：`CardPiles` 的单参构造内部用的是**无参 `new Random()`**
  （`CardPiles.java:27`）。`Combat` 创建 `CardPiles` 时走的正是这条路径，
  因此**每场战斗的洗牌与抽牌都不可复现**——同一个种子跑不出同一场战斗。
  这个测试让 20 血玩家打完一场普通战并断言 `VICTORY`，结果取决于抽牌运气。
- **本次改动会放大它**：普通战斗现在有约 29% 概率抽到双怪编队
  （`GameController.pickMonster` 的 BATTLE 分支改成 `MonsterCatalog.randomEncounter`），
  20 血玩家碰上两只怪时被击败的概率显著上升。

**建议**：
1. 把 `CardPiles` 的随机源从种子串起来（`CardPiles(logger, random)` 重载已经存在，
   只需让 `Combat` 透传一个由单局种子派生的 `Random`）。这同时也是**战斗可复现性**问题，
   直接影响数值试玩与 bug 复现，优先级高于这条测试本身。
2. 该测试改成不依赖「必赢」假设——例如钉住一个单怪遭遇，或允许 `DEFEAT`。

> 已确认与本次改动无关：单独运行该测试类连续 12 次全部通过；全量运行也多次 156/156 通过。
